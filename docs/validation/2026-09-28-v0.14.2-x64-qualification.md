## Trusted entry and evidence handling

The operator independently pinned the published launcher digest, read and hashed one bounded
byte buffer, then executed that same buffer in an elevated Windows PowerShell 5.1 process.
It installed the harness into an administrators-only Program Files directory. All 13 installed
files matched the receipt and source commit; the installation and ancestor ACL checks passed.
The runner and verifier were launched only from this protected installation, not a writable checkout.

The runner staged the authenticated candidate and byte-exact scripts exported from the commit,
ran the tests on disposable guests, sealed results before restoring checkpoints, and retained
the bootstrap receipt, harness manifest and candidate manifest with each evidence set.
Host logs record restoration of both VMs after the network run, including the target's original
network connection. The network password was entered only in the two guest credential dialogs.

After each run, `Verify-QualificationProvenance.ps1` from the protected installation was run
**unelevated**, with the external commit and launcher digest above: **12/12 checks passed**.
These cover exact evidence inventories and hashes, complete source-bound harness/candidate
inventories, bootstrap receipt, successful artifact-triplet identity, and refusal of ordinary-user
writes to evidence, seals, results, harness, candidates, VM storage and the protected root.
An operator invocation from an elevated console was correctly refused; the subsequent
unelevated verification passed. This was not a failed network test.

The seal is a SHA-256 inventory protected by host ACLs, not a digital signature or protection
against a malicious administrator. The verifier result does not replace a live pre-launch
substitution negative trial, which remains open.
